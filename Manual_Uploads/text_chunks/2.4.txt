The choice of microcontroller platform is one of the most important early decisions in any embedded system project. It determines what you can measure, how fast you can process it, and what you will spend months debugging later. In the DIY and research irrigation space, there are essentially three common platform families: Arduino (AVR-based), ESP32/ESP8266, and Raspberry Pi. STM32 appears occasionally in more technically demanding projects.

Arduino boards based on the ATmega328P are the most widely used platform in student and hobbyist irrigation projects. The reasons are obvious — low cost, large community, enormous library ecosystem, and a development environment that is genuinely accessible to beginners. For a simple project with one or two sensors, a few relay outputs, and no connectivity requirement, Arduino is perfectly adequate.

The limitations become significant when requirements grow. ATmega328P has 2 KB of RAM and a 16 MHz single-core processor. With a Wi-Fi module added, memory pressure becomes real fast. The single-core architecture means that if the code is busy doing an ADC conversion, it is not processing serial input at the same time. For a sensor module that needs to run ADC sampling continuously while also responding to serial commands and managing a multi-state irrigation sequence timer, the ATmega328P is simply undersized. Workarounds exist through careful interrupt design and memory management, but they add complexity that makes the firmware harder to read, debug, and change later.

ESP32 largely solves the connectivity problem. Dual-core 240 MHz processor, integrated Wi-Fi and Bluetooth, 12-bit ADC with 18 channels, and 520 KB of RAM make it a genuinely capable platform. Many recent irrigation research systems use ESP32 as the central controller, handling sensor reading, timer scheduling, relay output, and cloud communication all in one device. For projects that do not need extremely precise analog measurements, this approach works well and keeps the design simple.

The ADC on the ESP32 is worth mentioning honestly. It has known noise and nonlinearity issues, particularly on channels shared with the Wi-Fi subsystem during active transmission. For detecting whether soil moisture is above or below a rough threshold, this is fine. For measuring TDS with enough precision to drive a closed-loop fertilizer control system, the ESP32 ADC characteristics can be a real problem. Software filtering helps, but there is an inherent hardware limitation that cannot be fully compensated.

STM32 microcontrollers offer real advantages for measurement-intensive applications. The STM32F103C8T6 at 72 MHz has a 12-bit ADC with significantly better noise performance, flexible DMA for background data collection without interrupting the CPU, and timer peripheral capabilities that make implementing precise multi-channel timing straightforward. It also costs around 2 USD on the Blue Pill development board, which is competitive with the cheapest Arduino options.

The decision to use two separate STM32 boards — one for sensing, one for relay control — came from a real hardware design consideration, not from having extra budget. Running ADC conversions continuously on a system that also drives relay coils introduces electrical noise on the power and ground planes that corrupts ADC readings. Separating the sensor analog side from the relay switching side, and connecting them over a clean serial link, is standard practice in industrial instrumentation. For this project, it also simplified the firmware considerably. Each board does one thing well.

The Raspberry Pi appears in some irrigation discussions and it is worth addressing directly. It is a Linux computer running a full operating system. Boot time is 20 to 40 seconds. GPIO control from Linux is not deterministic because the OS scheduler can preempt your code at any moment. Power consumption is several watts continuously, compared to milliwatts for an STM32 or ESP32. At 35 to 80 USD it is the most expensive option on this list. For building a display terminal, a data logging server, or running computer vision, Raspberry Pi makes sense. For reading sensors and driving relays with precise timing, it is genuinely the wrong tool for this application.
